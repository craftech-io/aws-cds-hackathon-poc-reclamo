# FL-042 · Transferencia pendiente: seguimiento y acreditación

| Campo | Valor |
|---|---|
| Área | F · Transferencias y desembolsos |
| Actores | cliente (`C28`), agente, red |
| Canal | WhatsApp |
| Disparador | transferencia `PENDING` dentro del plazo de la red |
| Reglas | `CH-WA-CUSTOMER-INITIATED` (novedad de un reclamo propio), `LAM-ONCE-PER-EVENT` |
| Depende del modelo | Sí (ver Oráculo) |
| Fuente | `docs/flows-catalog.md` FL-042; `docs/test-plan.md` §2.2, §4.3 y §4.5 |

## Entrada

- Mundo `qa-<runId>-sc07`, reloj `PAUSED`.
- Persona clon de `C28`: transferencia `PENDING` dentro del plazo; el timer `NETWORK_TRANSITION` la pasa a `COMPLETED` el jue 08/10 12:00.

## Pasos

1. Reclamo; email; desafío; `get_transfer_status` → `PENDING`.
2. `update_complaint({status: AWAITING_NETWORK, followUpAtSim})` y explicación del plazo.
3. `conv.settleProbe`; `clock.advanceTo(2026-10-08T12:00-03:00)`.
4. `NETWORK_TRANSITION` → `COMPLETED` → turno `TRANSFER_STATUS_CHANGED` → `COMPLAINT_UPDATE` y respuesta escrita.
5. `conv.settleProbe`; `snapshot`.

## Resultado esperado

- **R1** · `statusHistory` = `AWAITING_NETWORK → INVESTIGATING → RESOLVED → ANSWERED`. _Dónde:_ `snapshot.complaints[].statusHistory`.
- **R2** · La bandeja muestra que el reclamo espera a la red, no al cliente. _Dónde:_ `console.inbox.list`.
- **R3** · Exactamente un `COMPLAINT_UPDATE` por el evento de la red; un segundo en el mismo turno devuelve `CONFLICT` (`LAM-ONCE-PER-EVENT`). _Dónde:_ `snapshot.conversation.messages`, `snapshot.turns[].results`.

Negativos (se asiertan después de la quiescencia, `CONVENCIONES.md`):

- **N1** · Ningún segundo `COMPLAINT_UPDATE` con el mismo `triggerEventId`.

## Oráculo

Fila `SC-07/1-6`, `SC-08/1-4` de §4.3. Hechos exigidos: evidencia `TRANSFER_STATUS` con el estado de la red; `AWAITING_NETWORK` mientras espera; un solo `COMPLAINT_UPDATE` por evento (lo impone el código). Alternativa aceptada: respuesta escrita por `ANSWER_DUE`.
