# FL-087 · Aprobación ejecutada por código

| Campo | Valor |
|---|---|
| Área | K · Humano en el circuito |
| Actores | operador |
| Canal | consola |
| Disparador | "Aprobar" con login reciente; un `APPROVAL_DECIDED` repetido o fabricado |
| Reglas | `recentLoginProcedure`, `CAP` |
| Depende del modelo | Sí (ver Oráculo) |
| Fuente | `docs/flows-catalog.md` FL-087; `docs/test-plan.md` §2.2, §4.3 y §4.5 |

## Entrada

- Mundo `qa-<runId>-sc16`; persona clon `C13'` con una aprobación `PENDING` pedida por el agente (camino de `FL-024`); y la de `SC-02/5`.
- Principal `OPERATOR` con `authTime` de hace 20 min y, después, con login reciente.
- `event.inject({type: APPROVAL_DECIDED, approvalId})` para una aprobación `PENDING` y, después de ejecutada, repetido.

## Pasos

1. `console.approvals.decide(APPROVED)` con `authTime` de hace 20 min → 403.
2. Con login reciente → aprobada; `APPROVAL_DECIDED` con solo el `approvalId`.
3. `execute_approved_action`: lectura fuertemente consistente, `EXEC#` condicional, monto recalculado con el core, claim de clave natural; turno para comunicar.
4. `event.inject` con el `approvalId` de otra aprobación todavía `PENDING`.
5. `event.inject` repetido con el `approvalId` ya ejecutado.
6. `conv.settleProbe`; `snapshot`.

## Resultado esperado

- **R1** · El intento sin login reciente responde 403 y no cambia nada. _Dónde:_ respuesta del procedimiento, `snapshot.complaints[].approvals`.
- **R2** · Con login reciente: una acción, `decidedBy`, `executedAt`, `AuditLog ACTION APPROVED` y `ACTION EXECUTED`. _Dónde:_ `snapshot.complaints[]`, `snapshot.audit`.
- **R3** · Los eventos fabricado y repetido terminan en `APPROVAL_NOT_EXECUTABLE` sin movimiento de dinero. _Dónde:_ `snapshot.audit`.
- **R4** · Una sola ejecución en total. _Dónde:_ `snapshot.complaints[].actions`.

Negativos (se asiertan después de la quiescencia, `CONVENCIONES.md`):

- **N1** · Ningún movimiento de dinero por un `APPROVAL_DECIDED` sin una aprobación `APPROVED` vigente.

## Oráculo

La precondición (una aprobación `PENDING` pedida por el agente) sigue la fila `SC-02/4`, `SC-05/3`, `SC-06/2`, `SC-21/8` de §4.3. La decisión, la ejecución y el descarte de eventos son código; alternativa aceptada solo para la respuesta escrita posterior (`ANSWER_DUE`).

## Pruebas que lo cubren

- **U (unitario)** · `routers/approvals.test.ts`, `worker/approval.test.ts` — `routers/approvals.test.ts` asierta `recentLoginProcedure` (403 sin login reciente) y que la decisión encola solo el `approvalId`; `worker/approval.test.ts`, que un evento sin aprobación `APPROVED`, repetido, de otra época, vencido o con el monto crecido no ejecuta.
- **UI (Playwright local)** · `approvals.spec.ts` — asierta el modal con `auth_time` de hace 20 min (contraseña → aprobado; cancelar → 403 sin efecto).
- **SR (escenario en `poc`)** · `SC-02/5`, `SC-16/5`, `SC-16/7`
  - `SC-02/5` (`docs/test-plan.md` §4.5): `console.approvals.decide` (`OPERATOR`, login reciente) → `execute_approved_action` imputa por código una vez → respuesta escrita
  - `SC-16/5` (`docs/test-plan.md` §4.5): `approvals.decide` con `authTime` de hace 20 min → 403; con login reciente → acción ejecutada una vez
  - `SC-16/7` (`docs/test-plan.md` §4.5): `event.inject(APPROVAL_DECIDED)` con el `approvalId` de una aprobación `PENDING` y, después de aprobada y ejecutada, el mismo evento repetido → `APPROVAL_NOT_EXECUTABLE`; una sola ejecución en total
